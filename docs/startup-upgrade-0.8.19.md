# Исправление запуска после обновления — 0.8.19

Сбой 0.8.18 воспроизведён на отдельной копии старой базы: процесс завершался с кодом 101
при запуске `Core::open` из setup Tauri. Новый профиль запускался успешно. В копии базы
достаточно было заменить только SHA-384 миграций 6/7 на LF-варианты, чтобы та же сборка
запустилась. Оригинальная база для этого эксперимента не менялась.

Локальные Windows-сборки включали CRLF-байты двух новых SQL-файлов. При коммите Git сохранял
LF, и сборка GitHub включала другой checksum того же SQL. SQLx корректно отказался открывать
базу с несовпадающей историей; прежние проверки свежего профиля этого не обнаруживали.

Исправление ядра:

- Новые миграции получают LF-байты независимо от редактора и checkout.
- Только для точного известного SQL миграций 6/7 допустим также исторический CRLF-checksum.
  Подменяется лишь ожидаемое значение в памяти валидатора; записи `_sqlx_migrations`
  не переписываются, SQL повторно не выполняется.
- Изменённый SQL, неизвестные checksum, отсутствующие и незавершённые миграции продолжают
  обрабатываться штатными проверками SQLx. Автоматического сброса или очистки базы нет.
- Опубликованные SQL-файлы не изменены. Явное правило `.gitattributes` фиксирует LF для SQL.

Регрессионные тесты проверяют повторное открытие старой и новой базы, сохранение чата,
аккаунта, событий и прав участника (миграция 6 не должна повторно сбрасывать их), применение
ещё не выполненной миграции 7 и отказ на повреждённую историю.

`scripts/native-upgrade-audit.mjs` создаёт базы только с фиктивными данными, запускает
готовый EXE для LF/CRLF-вариантов и проверяет snapshot, события и неизменность checksum.
Проверка добавлена в релизный workflow до публикации. Модельные запросы не выполняются.
